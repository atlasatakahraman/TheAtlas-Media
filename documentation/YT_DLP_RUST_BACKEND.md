# Rust-Native yt-dlp Backend Integration Plan

> **Revision history**
> - **2026-05-31** — Pivot from `rusty_ytdl` (pure Rust) to the boul2gom `yt-dlp` crate. The crate calls `yt-dlp` only for metadata extraction (`--dump-json`); actual downloads run on a native Rust HTTP client with parallel segmentation, documented at 2–4× faster than raw `yt-dlp`. See `docs/adr/ADR-005-yt-dlp-crate-pivot.md`.
> - **Initial** — original Rust-native goal as written below.

This document describes how to build TheAtlas Media Processing around a **Rust-native yt-dlp-compatible Rust crate** (the boul2gom `yt-dlp` crate) instead of (a) directly shelling out to the `yt-dlp` executable from React and (b) bundling and parsing the CLI ourselves from Rust. The frontend remains a responsive Next.js/React UI, while the Tauri Rust backend owns extraction, download orchestration, filesystem access, cancellation, and progress events.

The chosen crate technically depends on the standalone `yt-dlp` Python binary for metadata extraction, which it downloads and manages automatically via `LibraryInstaller`. This is treated as a managed runtime dependency, not a user-facing CLI integration: the binary is invoked only for `--dump-json` calls, never for the bytes-on-the-wire phase, and the React UI never sees CLI flags or stderr.

## Goals

- Use Rust/Tauri commands as the only bridge between the React UI and download execution.
- Use a Rust-native yt-dlp-compatible library inside the backend for extraction and download workflows.
- **Use the crate's native Rust HTTP downloader with parallel segmentation** for the actual download bytes. Allow the crate to invoke its managed `yt-dlp` binary only for metadata.
- Stream structured progress, logs, and terminal states to the frontend without blocking rendering.
- Keep file paths, request validation, format presets, and output naming controlled by the backend.
- Follow current React rendering performance guidance from the official React docs.

## Non-goals

- Calling `yt-dlp` directly from React.
- Parsing raw `yt-dlp` CLI stdout/stderr from our own code (the crate handles this internally).
- Accepting raw yt-dlp command-line flags from the UI.
- Adding manual React memoization everywhere before profiling shows a bottleneck.
- Bundling `yt-dlp` or `ffmpeg` as Tauri sidecars in `tauri.conf.json` `externalBin` for the default flow — the crate's `LibraryInstaller` manages both at runtime in the app's data directory.

## Rust-native yt-dlp integration model

The backend depends on the boul2gom `yt-dlp` Rust crate (v2.7.x). This crate is wrapped by an internal service so the rest of the app is not coupled to it directly — an `ExtractorBackend` trait sits between `DownloadService` and the crate, with a second (off-by-default) implementation that wraps a user-provided yt-dlp + ffmpeg CLI for corporate or air-gapped environments.

Recommended backend shape:

```text
React UI
  -> Tauri command: start_download(request)
  -> Rust DownloadService
  -> Rust-native yt-dlp-compatible library
  -> Rust file/output/post-processing layer
  -> Tauri events: download://progress, download://log, download://finished, download://failed
```

Backend rules:

1. Keep all download and extraction calls inside Rust.
2. Validate URLs before handing them to the library.
3. Map UI format choices to app-defined Rust presets.
4. Do not expose arbitrary library options directly to the frontend.
5. Canonicalize output directories before writing files.
6. Keep all generated output inside the selected output directory.
7. Convert library progress callbacks into small typed Tauri events.
8. Convert library errors into stable app errors before returning them to React.
9. Keep the library behind a trait so it can be swapped if the chosen crate changes.

`ffmpeg` and `ffprobe` are required for merging separate audio/video streams and for post-processing (chapter embedding, precision trimming). With the chosen crate they are **installed and invoked by the crate itself** via `LibraryInstaller::install_ffmpeg()` and the crate's internal post-processing pipeline. We surface their availability and version through a `get_diagnostics` Tauri command, and let the user trigger a re-install via `update_yt_dlp` (which refreshes both binaries). We do not invoke `ffmpeg` ourselves in v0.1.

## Rust backend architecture

Add a small download domain to the Tauri backend.

### Core backend pieces

- `DownloadRequest`
  - URL
  - output directory
  - format preset
  - optional filename template
  - optional post-processing options
- `DownloadId`
  - generated by the backend
  - used to correlate events and cancellation
- `DownloadService`
  - validates requests
  - resolves format presets
  - calls the Rust-native yt-dlp-compatible library
  - normalizes progress and errors
- `DownloadManager`
  - owns active download tasks
  - prevents duplicate starts where appropriate
  - supports cancellation through cancellation tokens or task handles
- `DownloadEvent`
  - progress percentage if available
  - downloaded bytes / total bytes if available
  - speed / ETA if available
  - current phase: resolving, downloading, merging, postprocessing, complete, failed, cancelled
- `ExtractorBackend` trait
  - hides the concrete Rust library from Tauri commands
  - exposes `extract_info`, `download`, and `cancel`-aware operations

### Internal trait boundary

Use an internal trait to prevent the app from depending directly on one crate's public API everywhere:

```rust
trait ExtractorBackend {
    async fn extract_info(&self, request: ExtractInfoRequest) -> Result<MediaInfo, DownloadError>;
    async fn download(
        &self,
        request: DownloadRequest,
        progress: ProgressSink,
        cancellation: CancellationToken,
    ) -> Result<DownloadResult, DownloadError>;
}
```

The Tauri commands should call `DownloadService`, not the library directly.

### Download execution

The Rust backend should:

- Create a backend-generated `DownloadId`.
- Validate and normalize the URL.
- Canonicalize the output directory.
- Resolve the requested format preset to backend-owned options.
- Start the library download in an async task.
- Forward progress callbacks to Tauri events.
- Respect cancellation tokens.
- Perform post-processing only through backend-approved operations.
- Emit one terminal event: complete, failed, or cancelled.

### Format presets

The UI should select from app-defined presets instead of providing raw library options.

Initial presets:

- `BestVideoAudio`
  - best video plus best audio, merge when needed
- `BestAudio`
  - audio-focused download or extraction
- `Mp4Compatible`
  - prefer formats that work well in common players
- `MetadataOnly`
  - extract title, duration, thumbnail URL, and available formats without downloading

## React frontend architecture

React should only manage UI state and invoke Tauri commands. Heavy work, extraction, download management, post-processing, and filesystem decisions belong in Rust.

Recommended frontend shape:

```text
DownloadPage
  -> DownloadForm
  -> DownloadQueue
     -> DownloadQueueItem
        -> ProgressBar
        -> DownloadActions
```

State should be kept as local as possible:

- Keep form draft state inside `DownloadForm`.
- Keep per-download progress state keyed by `downloadId`.
- Avoid putting high-frequency progress events in a top-level provider unless many unrelated components need them.
- Batch or throttle progress updates if events arrive faster than the UI can usefully render.

## React rendering and cascade performance guidance

This project should follow the current official React guidance:

- A component renders on initial render or when its own state or an ancestor's state updates.
- Rendering is recursive: when a parent renders, React may render nested children too.
- Updating state high in the tree can cascade through many descendants.
- Rendering should stay pure; side effects belong in event handlers or Effects.
- React only commits DOM changes when output differs, but expensive render calculations can still hurt responsiveness.
- Do not optimize prematurely; use profiling before adding broad memoization.

Practical rules for this app:

1. Keep high-frequency download progress state close to the list/item that displays it.
2. Do not store rapidly changing progress in `AppView`, `Header`, or other global layout components.
3. Split static layout from dynamic download rows so progress updates do not re-render the whole shell.
4. Prefer passing primitive props such as `id`, `status`, `percent`, and `filename` to row components.
5. Avoid creating new object and function props for memoized children on every render.
6. Use `memo` only for components that re-render often with unchanged props and have noticeable render cost.
7. Use `useMemo` for expensive derived values, stable object/array props passed to memoized children, or hook dependencies that must remain stable.
8. Use `useCallback` when a stable function is passed to a memoized child or used as another hook dependency.
9. Prefer moving functions or objects inside an Effect instead of memoizing them only to satisfy Effect dependencies.
10. Use React DevTools Profiler or production-mode measurements before adding custom comparison functions.

## Event flow

1. User submits a URL in React.
2. React calls `start_download` through Tauri.
3. Rust validates the request and creates a `DownloadId`.
4. Rust calls the internal `DownloadService`.
5. `DownloadService` calls the Rust-native yt-dlp-compatible backend library.
6. Rust receives library progress callbacks and emits typed Tauri events.
7. React listens for events matching the `DownloadId`.
8. React updates only the affected queue item.
9. Rust emits a terminal event when the download task completes, fails, or is cancelled.
10. React marks the item complete, failed, or cancelled.

## Error handling

Backend errors should be normalized before reaching React:

- `ExtractorUnavailable`
- `UnsupportedSite`
- `InvalidUrl`
- `InvalidOutputDirectory`
- `FormatUnavailable`
- `PostProcessorUnavailable`
- `DownloadFailed { message }`
- `Cancelled`

The frontend should render these as user-facing messages without exposing raw internal paths unless useful for troubleshooting.

## Security considerations

- Do not expose raw library options or yt-dlp-style flags to untrusted UI fields.
- Use app-defined presets for formats and post-processing.
- Canonicalize output paths and prevent path traversal.
- Keep generated filenames inside the selected output directory.
- Avoid arbitrary plugin/script loading unless explicitly reviewed.
- Treat downloaded filenames, titles, descriptions, and thumbnails as untrusted display data in React.
- Validate all backend boundary inputs from Tauri commands.

## Implementation plan

### Phase 1: Backend foundation

1. Select and evaluate the Rust-native yt-dlp-compatible crate. **Chosen (2026-05-31):** boul2gom `yt-dlp` v2.7.x with `default-features = false` and features `cache-memory`, `hooks`, `statistics`, `rustls`, `hickory-dns`. See ADR-005.
2. Add Rust request/response/event types for downloads.
3. Add an internal `ExtractorBackend` trait around the selected crate.
4. Add a `DownloadService` that validates requests and calls the trait.
5. Add a `DownloadManager` to track active async tasks by `DownloadId`.
6. Add a `start_download` Tauri command.
7. Add a `cancel_download` Tauri command.
8. Detect `ffmpeg` and `ffprobe` only for presets that require post-processing.
9. Convert library errors into stable app errors.

### Phase 2: Frontend queue UI

1. Add a download form for URL and format preset selection.
2. Call `start_download` from the form submit handler.
3. Add a queue state model keyed by `DownloadId`.
4. Subscribe to Tauri download events in the smallest component that owns queue state.
5. Render one row per active or completed download.
6. Wire cancellation to `cancel_download`.
7. Keep progress updates out of global layout state.

### Phase 3: Performance pass

1. Profile progress updates with multiple concurrent downloads.
2. If rows re-render unnecessarily, wrap `DownloadQueueItem` in `memo`.
3. Stabilize callback props with `useCallback` only where memoized children benefit.
4. Stabilize derived arrays or grouped queue data with `useMemo` only if profiling shows cost.
5. Throttle high-frequency progress events if React commits become too frequent.
6. Avoid custom `memo` comparison unless measured faster than re-rendering.

### Phase 4: Packaging and release readiness

1. Document the selected Rust-native library and its license.
2. Document any remaining external runtime dependency such as `ffmpeg`.
3. Add diagnostics for extractor availability and post-processing support.
4. Test downloads, cancellation, failed URLs, unsupported sites, missing post-processors, and invalid output paths on supported platforms.
5. Verify release builds do not depend on a user-installed `yt-dlp` executable for normal operation.

## Acceptance criteria

- React never invokes `yt-dlp` or extractor logic directly.
- The Rust backend uses a Rust-native yt-dlp-compatible library for normal extraction and download flows.
- The app does not spawn the `yt-dlp` CLI for normal downloads.
- A download can be started, monitored, completed, failed, and cancelled.
- Progress updates only re-render the affected queue UI, not the full app layout.
- Missing post-processing dependencies produce clear user-facing errors.
- Output paths are controlled and validated by the backend.
